T3N Agent Build Challenge

Purpose and usefulness

TrustGate demonstrates how an enterprise agent can remain inside a bounded mandate. It authenticates through T3N, binds a purchase request to the returned DID, and checks identity, action, resource, approval and spend limits before permitting execution.

Architecture

T3N handshake and authentication ? authenticated DID ? request bound to that DID ? identity comparison ? deterministic policy ? decision and redacted audit metadata.

The TypeScript authentication adapter, policy engine, and audit layer are separate and small enough to inspect and maintain. Unknown actions and resources are denied. Requests above 250 require approval; requests above 1000 are denied even with approval.

Security and outstanding scope

The current adapter uses unsafe_trust_server only in sandbox and rejects other environments. It does not establish production server trust. Current T3N documentation recommends a verified trust manifest for hosted nodes. Approval is a caller-provided boolean; production needs verified approval provenance. Redaction is based on metadata field names, not arbitrary secret detection. Inputs are typed internal calls, not a hardened public API.

The full TEE-contract walkthrough, contract deployment, agent delegation, and enclave-hosted execution have not been demonstrated. Independent security review remains pending. This submission must not be represented as completion of those steps.

Maintenance and handover

Preferred handover: sponsor maintains and runs this small repository. Install from the lockfile, provision sponsor-owned credentials, run build/tests/demo and live verification, and review SDK upgrades and trust configuration before hosting. No ongoing hosting or support commitment is assumed. Dependencies and build output are excluded from tracking. Credentials remain private.
